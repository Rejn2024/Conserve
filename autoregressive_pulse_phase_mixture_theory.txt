Autoregressive pulse controls: theory and implementation notes
==================================================================

1. Problem being solved
-----------------------
The controller previously emitted model_out["pulse_phase_rel_rad"] as one bounded scalar per pulse slot.  That representation can only express a single deterministic phase trajectory at the controller-output level, and the ActorCritic wrapper placed a factorized Normal distribution over the flattened action vector.  A factorized unimodal Normal is poorly matched to pulse phase control because useful phase schedules can be multi-modal: for example, a policy may want either an alternating phase-inversion pattern, a monotone phase walk, or a reset-like pattern for the same observation.

2. Why phases need circular mixture distributions
-------------------------------------------------
Pulse phases live on a circle.  The numerical values -pi and +pi represent nearby physical phases, not distant endpoints.  Treating phase with an ordinary line distribution creates artificial boundary discontinuities.  The implementation therefore keeps every phase wrapped with atan2(sin(x), cos(x)) and models each pulse step with a mixture of wrapped Gaussian components.  Each component has:

  * logits: unnormalized mixture weights,
  * loc_rad: a component location on [-pi, pi], and
  * concentration: an inverse-variance-like positive precision.

Sampling selects a component and then samples a local Gaussian perturbation around its circular location before wrapping the result back to [-pi, pi].  Log probabilities approximate the wrapped density by evaluating the component Normal density at phase shifts of -2*pi, 0, and +2*pi and log-summing those aliases.

3. Why the model is autoregressive
----------------------------------
The decoded pulse rotations are cumulative: later pulse rotations depend on earlier relative increments.  A fully independent mixture per pulse slot would represent multiple modes, but it would not model the sequential dependence between pulse decisions.  The autoregressive factorization is:

  p(phi_1, phi_2, ..., phi_N | observation)
    = product_i p(phi_i | phi_1, ..., phi_{i-1}, observation)

The code embodies this with an LSTM decoder in TonePulseTXControlNetVarLen.  The fused observation embedding initializes the recurrent hidden and cell states, each step consumes sin(previous_phase), cos(previous_phase), sin(index_angle), and cos(index_angle), and the current LSTM hidden state emits mixture logits, circular locations, and concentrations for the next pulse-relative phase.

4. Deterministic controller output
----------------------------------
The synthesis path still needs a tensor named model_out["pulse_phase_rel_rad"] so existing decode_tone_pulse_config and apply_tone_pulse_action_overrides logic can continue to operate.  In deterministic controller forward passes, the code computes the circular mean of the mixture at each autoregressive step and stores that mean trajectory under model_out["pulse_phase_rel_rad"].  It also returns the full distribution parameters:

  * model_out["pulse_phase_rel_mix_logits"],
  * model_out["pulse_phase_rel_mix_loc_rad"], and
  * model_out["pulse_phase_rel_mix_concentration"].

This preserves backward compatibility while making the distributional structure available for RL and diagnostics.

5. ActorCritic policy integration
---------------------------------
The ActorCritic flattened action dimension is now 12 + 4*max_tones.  Pulse phase, log-length, and power sequences are generated by recurrent decoders in the controller backbone; the flat action row stores only three Gaussian sequence-level controller parameters that govern those recurrent decoders.
The 12 fixed scalar dimensions are five leading global controls (`noise_color`, `fading_mode`, `rf_center_delta_hz`, `carrier_hz_norm`, `num_tones`) plus seven trailing controls after the four tone vectors (`tone_phase_offset_rad`, `pulse_phase_ar_control`, `pulse_length_ar_control`, `pulse_power_ar_control`, `pulse_phase_offset_rad`, `pulse_count`, `start_offset`). Pulse on/off samples are derived from recurrent pulse lengths and contiguous-pulse semantics, not action dimensions.

  * pulse_phase_autoregressive_mixture(...) still produces model_out["pulse_phase_rel_rad"] for synthesis,
  * pulse_length_power_autoregressive(...) produces model_out["pulse_length_log"] and model_out["pulse_power_logit"],
  * `log_std_head` emits a `[batch, action_dim]` log-standard-deviation tensor aligned one-for-one with `action_mean`, so the three recurrent-controller columns get Gaussian stds at the same indices as their means,
  * the flat action log_prob/entropy covers non-sequential Gaussian dimensions plus the three Gaussian recurrent-controller parameters, and
  * dict overrides can still inject pulse phase/length/power sequences for scripted policies or diagnostics.

This means the phrase "non-phase Gaussian controls plus the AR pulse phase distribution" is replaced by a cleaner Gaussian-controller view: phase, length, and power each contribute one Gaussian recurrent-controller parameter to the flat action row.

6. Variable pulse length and power semantics
--------------------------------------------
The length/power LSTM emits model_out["pulse_length_log"] and model_out["pulse_power_logit"].  Synthesis converts exp(pulse_length_log) to integer sample lengths clamped to [5, 10000].  Pulse off time is forced to zero, so each pulse begins immediately after the previous pulse ends.  Power logits are converted through sigmoid and used as per-pulse amplitude multipliers during the tone overlay.

7. Notebook SAC integration
---------------------------
RL_Jamming_test_02.ipynb keeps the flat SAC action vector focused on ordinary non-sequential controls.  The pulse phase/length/power recurrent decoders remain in the controller backbone and no longer widen the action row.

8. accelerated_training_utils integration
-----------------------------------------
The environment action normalizer decodes the reduced flattened ActorCritic action vector.  When the vector length matches 12 + 4*max_tones, no per-pulse sequence is decoded from flat columns; only compact recurrent-controller parameters are decoded.  Pulse_phase_rel_rad, pulse_length_log, and pulse_power_logit can still be supplied explicitly in dict overrides for diagnostics or scripted policies, but they are not required columns in the standard flat action row.

9. Why recurrent policy state reduces action_dim
------------------------------------------------
The previous max_pulses terms were not mathematical requirements of the waveform generator; they were compatibility choices for storing phase, log length, and power in one dense actor/critic/replay-buffer row.  By treating all three pulse attributes as recurrent controller state governed by three Gaussian parameters, the flat row no longer needs padded per-pulse columns while still accounting for these controls in log-prob/entropy.  A fully structured sequence-action API could expose those recurrent sequences directly, but that would require recurrent replay state/masks, sequence-aware critics, off-policy burn-in or stored hidden states, and an environment adapter that accepts structured pulse sequences rather than one dense row.
